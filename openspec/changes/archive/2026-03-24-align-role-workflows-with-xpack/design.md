## Context

foundation change 先锁定了组织边界、用户归属、默认角色和身份上下文；role workflows 需要在此之上把“角色作为业务对象”的生命周期和运营入口补齐。官方手册强调的重点不是抽象权限引擎，而是角色创建、成员挂载、继承约束、最后角色保护和前端统一入口，因此本 design 要避免角色逻辑再次回流到 foundation 或越界进入 permission center。

## Goals / Non-Goals

**Goals:**
- 稳定角色 CRUD、成员管理、继承约束和唯一角色安全策略的系统行为。
- 明确组织用户与外部用户的角色挂载流程及其幂等约束。
- 让角色工作流在用户管理页的 IA 中可达、可操作、可验证。

**Non-Goals:**
- 不在本 change 中承载菜单/资源/行列权限的统一配置。
- 不重写 foundation 已确定的组织、用户、登录主数据语义。
- 不引入新的角色权限计算引擎。

## Decisions

1. role workflows 只定义角色生命周期与成员运营，不定义完整授权编排。
   - Why: Oracle 明确指出角色是业务对象，权限是授权对象，两者必须分层。
   - Alternative: 在 role workflows 中一并完成角色授权配置；被拒绝，因为会与 permission center 产生重叠。

2. 角色成员添加分为“组织内用户选择”和“外部用户精确检索”两条治理路径。
   - Why: 官方手册要求这两种入口语义不同，且外部用户挂载需要更强审计和范围校验。
   - Alternative: 统一为一个搜索框；被拒绝，因为会弱化组织边界并增加误操作。

3. 最后角色安全策略必须由后端强约束而不是仅前端提示。
   - Why: 这是核心一致性规则，必须在接口和服务层保证确定性。
   - Alternative: 只保留前端确认弹窗；被拒绝，因为无法防止 API 直调绕过。

4. 角色工作流继续托管在用户管理页的角色页签内，但能力归属仍属于 `role-management`。
   - Why: IA 与领域职责要分开：入口在用户管理，规范责任在角色能力。
   - Alternative: 重新恢复独立角色主菜单；被拒绝，因为与现有 `role-in-user-management` capability 冲突。

## Risks / Trade-offs

- [角色工作流与权限中心边界混淆] → 在 spec delta 中显式声明“授权配置不属于本 change”。
- [最后角色策略与历史数据行为冲突] → 在 tasks 中加入策略冻结和回归样本验证。
- [组织内/外部用户挂载口径不一致] → 要求接口层保留明确入参和审计字段，避免隐式推断。
- [前端角色页签与后端契约不同步] → 将 IA 验收和 API 验收拆成独立 tasks，先锁契约再改页面。

## Migration Plan

1. 基于 foundation 输出的组织与用户查询能力，冻结角色 CRUD 和成员运营接口契约。
2. 先补角色成员与继承约束的 spec delta 和 failing tests。
3. 实现阶段先落后端服务/handler，再接前端角色页签与用户管理页内嵌工作流。
4. 在 permission center 开始前做一次角色载体验收，确认角色查询、成员挂载和继承边界稳定。
5. 回滚时保留旧页面入口或兼容 handler，但不得回滚 foundation 主数据契约。

## Open Questions

- 最后角色安全策略最终落为“禁止移除”还是“移除即禁用/删除用户”，需要在实现前锁定一个确定策略。
- 外部用户挂载是否允许模糊搜索，还是必须保持精确账号/ID 检索。
- 自定义角色继承时，是否需要显式记录父角色快照以支持后续审计与差异比较。
