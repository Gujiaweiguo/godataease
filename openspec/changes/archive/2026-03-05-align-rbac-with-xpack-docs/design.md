## Context

当前系统采用 Go 后端 + Vue3 前端，RBAC 基础链路可用，但与 DataEase v2 X-Pack 文档在“用户批量导入、角色成员管理、继承约束、双视角权限配置”方面存在差距。现有实现已经覆盖组织树和基础权限模型，重构目标是保留既有模型（用户、角色、组织、权限、菜单）并补齐关键业务能力。

## Goals / Non-Goals

**Goals:**
- 在不推翻现有数据模型的前提下，补齐文档定义的关键能力。
- 保证兼容接口与前端页面能力一致，避免“前端有入口、后端无能力”的断链。
- 提供可验证的阶段化迁移与回滚机制。

**Non-Goals:**
- 不删除组织/角色/权限任一核心模块。
- 不重构为全新权限引擎（如替换为 Casbin 全量改造）。
- 不在本 change 中实现菜单管理控制台（由独立 change 承担）。

## Decisions

1. 保持现有核心表结构，优先通过服务与接口补齐能力。
   - Why: 降低迁移风险，避免一次性 schema 变更导致权限回归。
   - Alternative: 先改 schema 再改服务；被拒绝，风险高且验证成本大。

2. 用户导入采用“模板校验 + 部分成功 + 错误报告下载”策略。
   - Why: 与官方文档一致，且避免全量失败带来的运维成本。
   - Alternative: 全有或全无导入；被拒绝，不符合文档行为。

3. 角色成员管理引入“唯一角色保护”强约束。
   - Why: 文档要求最后一个角色移除时用户删除/保护需要明确且可验证。
   - Alternative: 仅前端提示；被拒绝，后端缺少强一致保障。

4. 权限配置双视角统一落到同一授权模型。
   - Why: 降低实现复杂度，确保“按用户/按资源”结果一致。
   - Alternative: 双模型并行；被拒绝，后期维护成本高。

## Risks / Trade-offs

- [导入流程复杂导致边界 Bug] -> 增加模板契约测试、错误样本回归测试。
- [角色成员删除语义与历史行为冲突] -> 引入开关和审计日志，先灰度。
- [权限双视角改造影响现有页面] -> 保持 API 向后兼容，先增量再替换。
- [组织删除资源处置策略争议] -> 在实现前锁定策略文档并做数据备份。

## Migration Plan

1. 先补后端能力（导入、重置密码、角色成员管理、双视角接口）并保留旧接口。
2. 前端逐页启用新能力并保留旧入口 fallback。
3. 增加集成测试与契约测试门禁（用户、角色、权限、组织）。
4. 分阶段发布：先测试环境 -> 灰度组织 -> 全量。
5. 回滚：通过功能开关切回旧流程，数据库仅做可逆增量字段变更。

## Open Questions

- “唯一角色移除后用户删除”在当前 fork 是否沿用原文档，还是改为“禁止移除最后角色”。
- 组织删除时资源处置是“同步删除”还是“异步回收任务”。
- 用户来源（LDAP/OIDC/飞书等）导入字段是否全量启用，还是按部署配置启用。
