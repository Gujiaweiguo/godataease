## Context

当前仓库把 `godataease-app` 定义成发布型镜像：后端通过多阶段 Docker 构建生成 Go 二进制，前端通过 `apps/frontend/dist/` 打包后再复制进最终镜像，`docker compose` 只挂载数据和日志卷，不挂源码卷。这意味着日常开发中每次代码修改都要经过“前端重打包 / 后端重编译 / 重新构建镜像 / 重启容器”这条长链路，反馈周期远高于本地开发预期。

仓库已经具备在宿主机构建前端 `dist` 和后端二进制的能力，也已经验证过这些产物可以直接组装进运行时镜像。问题不在于缺少构建能力，而在于缺少一套被明确约束、文档化并与生产模式保持一致边界的统一工作流：开发者要么重复重建整镜像，要么绕开容器直接本地运行，导致团队对“标准开发环境”理解不一致。

本次 change 需要解决的不是单纯“让 Docker 更快”，而是定义一套可长期维护的开发/生产双模式约定：开发模式与生产模式都保持 app 运行在容器中，但开发模式通过文件挂载宿主机构建产物来减少镜像重建，生产模式继续优先可重建、可交付、可部署，并且两者尽量复用相同的配置模型、端口、入口和健康检查语义。

## Goals / Non-Goals

**Goals:**
- 明确 DataEase 本地开发模式的标准入口，使前端构建产物和后端二进制可以通过挂载方式进入 `godataease-app` 容器，而不再默认依赖重建镜像才能生效。
- 保留当前生产镜像构建路径，避免为了开发提速而破坏生产交付一致性。
- 统一开发模式与生产模式的关键运行约定，包括端口职责、依赖服务来源、健康检查入口和 app 容器职责边界。
- 让团队成员能快速判断“什么时候应该重建构建产物并重新加载容器”，而不是默认重建整镜像。

**Non-Goals:**
- 不将生产容器改造成带源码级热重载的长期开发容器。
- 不在本次变更中引入新的后端框架、前端构建器或大型外部开发工具链迁移。
- 不改变业务 API、权限逻辑、菜单语义或运行时功能行为。
- 不要求开发模式具备前端 HMR 或后端源码级热重载体验；本次目标优先是统一运行环境和减少镜像重建。

## Decisions

### Decision 1: 采用“同一 app 容器 + 不同产物来源”的双模式约定

**Decision**
- 开发模式：`godataease-app` 仍在容器中运行，但前端 `dist` 与后端二进制由宿主机构建，并通过挂载方式进入容器。
- 生产模式：继续使用当前 `Dockerfile + docker compose` 的镜像化运行路径，前后端构建产物被打包进 `godataease-app`。

**Rationale**
- 当前瓶颈来自“代码改动必须重建镜像”，而不是容器基础系统本身；改为挂载已构建产物可以去掉最重的一步，同时保持应用仍然在容器中运行。
- 这种模式在开发与生产之间保留了更强的运行环境一致性，适合把容器继续作为标准 app 载体。

**Alternatives considered**
- **继续只用单一 app 容器做开发和生产，且所有代码改动都重建镜像**：看似统一，实则把日常开发绑定到发布型镜像重建，反馈仍旧过慢。
- **将 app 容器切换到 Ubuntu 24.02**：会改变基础镜像和包管理体验，但不会解决源码未挂载、无热更新、每次都要 build 的主因。
- **前后端完全宿主机运行**：反馈更快，但会降低开发与生产的运行载体一致性，不符合当前优先级。

### Decision 2: 统一“端口和入口语义”，保持 app 容器对外入口一致

**Decision**
- 开发模式下维持 `godataease-app` 继续对外暴露 `:8080`，但容器内部读取的是宿主机挂载进来的前端 `dist` 与后端二进制。
- 生产模式下维持 `godataease-app` 暴露 `:8080`，对外同时承载前端静态资源和后端接口。
- 在文档与脚本层明确两种模式的健康检查、配置路径、挂载边界和产物刷新方式。

**Rationale**
- 用户看到的是统一的 app 容器入口：开发看 `:8080` 页面，生产也看 `:8080` 页面；差别只在产物来源不同。
- 这能减少“开发环境是本地进程、生产环境是容器”带来的环境心智切换。

**Alternatives considered**
- **在容器内直接挂载源码并引入 dev server / 热重载**：开发体验更强，但复杂度、文件监听稳定性和工具链维护成本更高，不符合本次最小方案。

### Decision 3: 将 compose 定位为开发和生产的共同运行入口

**Decision**
- 为 compose 明确两类职责：
  1. 开发模式下承载 app 容器与依赖服务，app 容器通过挂载宿主机构建产物运行
  2. 生产/集成验证场景下承载镜像化构建产物运行
- 开发文档和脚本中不再把“修改代码后 `docker compose up --build`”作为首选迭代路径，而是改为“更新构建产物并重新加载容器”。

**Rationale**
- compose 已经是团队当前最熟悉的应用运行入口，把它保留下来能降低切换成本。
- 通过挂载构建产物而非源码，可以避免把发布型容器彻底改造成复杂的源码热更新容器。

**Alternatives considered**
- **把 compose 彻底降级为只跑依赖**：开发反馈会更快，但会弱化开发与生产的运行环境统一性。

### Decision 4: 保留生产 Dockerfile，并补充开发产物刷新入口

**Decision**
- 生产 Dockerfile 继续用于镜像交付。
- 本次 change 预期补充最小开发入口，例如：
  - 开发产物构建说明/脚本
  - app 容器挂载说明
  - 必要的 compose override 或 helper script（若确有必要）
- 不把发布型 Dockerfile 改造成承担源码级热更新职责的唯一入口。

**Rationale**
- 这样可以把“镜像交付”和“开发迭代”分层处理：生产依赖镜像构建，开发依赖宿主机构建产物刷新。

**Alternatives considered**
- **只改文档，不补任何脚本/入口**：容易继续依赖口口相传，团队成员仍然可能误用 `compose up --build` 做日常开发。

## Risks / Trade-offs

- **[Risk] 开发模式仍然需要重新生成 `dist` 和二进制，反馈速度不如源码热更新** → **Mitigation:** 将本次方案限定为“减少镜像重建”而非“提供 HMR 级别体验”，并通过脚本降低产物刷新成本。
- **[Risk] 挂载产物可能导致容器读取旧文件或路径配置错误** → **Mitigation:** 统一产物输出路径、挂载路径和重载步骤，并提供命令级验证方法。
- **[Risk] 团队成员继续误把 `compose up --build` 当默认迭代路径** → **Mitigation:** 在文档、脚本命名和开发入口上明确“产物刷新运行”与“镜像重建运行”的区别。
- **[Risk] 本地运行依赖宿主机 Node/Go 环境，导致构建产物差异** → **Mitigation:** 明确最低版本与标准命令，必要时提供检查脚本或环境准备说明。
- **[Risk] 旧的 compose 镜像缓存让开发者误判代码未生效** → **Mitigation:** 在设计中明确镜像重建仅用于生产/集成路径，并保留可验证的健康检查与回归步骤。
- **[Risk] 为了统一而过度设计，反而增加维护成本** → **Mitigation:** 限制本次变更只解决开发入口、模式边界和最小脚本支持，不引入大型工具链重构。

## Migration Plan

1. 定义并落地标准开发启动路径：宿主机构建前端 `dist` 与后端二进制，compose 中的 app 容器通过挂载方式消费这些产物。
2. 补充必要脚本或 override 配置，使团队成员能一条命令完成产物刷新或快速进入开发模式。
3. 更新文档，明确开发模式与生产模式的职责边界、挂载语义、健康检查语义与镜像职责。
4. 保留并验证现有生产镜像构建路径，确保新开发模式不会破坏镜像化交付。
5. 用一次实际回归验证“开发改代码不再需要重建整镜像，同时生产镜像仍可正常构建运行”。

## Open Questions

- 是否需要提供单独的 `docker-compose.dev.yml`/override，还是仅通过现有 compose 配置加挂载脚本就足够。
- 是否需要为前端和后端补统一的"重建产物 + 重载容器"聚合入口脚本，以进一步降低新成员上手成本。
- 是否需要支持可选的宿主机直跑模式作为 fallback，而不是标准主路径。
