## Context

这次变更只重组导航信息架构，不引入新的业务域能力。当前运行时导航由后端 `core_menu` 数据驱动，前端基于授权菜单树渲染顶部与侧边导航；右上角 `MoreMenu` 和 `AccountOperator` 仍保留部分硬编码入口，因此实际入口分布在数据库菜单、头部弹出菜单和用户下拉菜单三处，语义不一致。

本 change 的核心是把“组织与权限治理”与“系统配置”分开，把工具类入口收敛到可扩展的一级「工具箱」，并删除非核心业务的帮助链接入口。实现需要同时修改 MySQL 菜单迁移、前端 shell 组件和 E2E 断言，但不应改动用户管理、组织管理、权限管理、当前数据库基线中的系统设置子项（如菜单管理与审计相关页面）以及导出中心本身的业务逻辑。

## Goals / Non-Goals

**Goals:**
- 将当前「系统管理」拆分为「组织权限」和「系统设置」，让管理员导航分组与职责边界一致。
- 将「菜单管理」归入系统配置语义，将「工具箱」升级为可扩展的一级菜单，并保留「数据导出中心」作为其二级项。
- 删除右上角 More 菜单及其帮助外链入口，移除用户菜单中的系统设置快捷入口。
- 保持运行时导航继续由 `core_menu` 与 `sys_role_menu` 驱动，避免前端重新引入硬编码分组判断。

**Non-Goals:**
- 不重写菜单树生成、权限校验或路由注册机制。
- 不改变用户管理、组织管理、角色管理、权限配置、当前数据库基线中已存在的系统设置相关页面以及导出中心的页面功能和 API 语义。
- 不在本次 change 中新增新的工具箱业务项或恢复帮助链接为其他展示形式。

## Decisions

1. **以数据库菜单迁移作为信息架构调整的唯一事实来源。**
   - Why: 当前顶部/侧边导航本身已经是后端菜单树驱动，一级分组调整最稳定的做法是修改 `core_menu` 的层级、排序、可见性和授权，而不是在前端临时拼接新分组。
   - Alternative: 仅在前端按 path 重新分组现有菜单；被拒绝，因为这会与 `menu-management` 的“数据驱动菜单”要求冲突，也会让角色菜单授权与可见性脱节。

2. **「组织权限」与「系统设置」都作为一级 group 菜单存在，且继续由角色授权控制。**
   - Why: 用户/组织/角色/权限属于治理入口，菜单管理及当前数据库中保留的系统设置子项属于系统配置入口，两者职责不同但都需要管理员权限；拆成两个一级组能降低侧边栏认知负担，同时保持现有 RBAC 模型不变。
   - Alternative: 继续保留单一「系统管理」分组，或把「菜单管理」留在组织权限下；被拒绝，因为这会继续混淆“授权治理”和“系统配置”边界。

3. **工具箱保留为一级 group，数据导出中心作为二级 event 菜单。**
   - Why: 用户已经明确希望为后续工具扩展保留层级空间；沿用 group + child 的菜单模型，也能避免未来再做一次 IA 迁移。
   - Alternative: 让工具箱成为直接点击的一级 event 菜单；被拒绝，因为虽然当前更扁平，但会把未来扩展成本转移到下一轮结构调整。

4. **删除 MoreMenu，而不是仅通过外观配置隐藏帮助项。**
   - Why: 本次方案是明确移除帮助文档、论坛、博客、试用等入口，而不是做条件隐藏；保留组件只会增加壳层复杂度和残留状态。
   - Alternative: 保留 `MoreMenu.vue`，仅通过 `showDoc` 或菜单数据把帮助项隐藏；被拒绝，因为这样会留下无业务价值的头部入口与维护负担。

5. **用户菜单继续保留“关于 / 修改密码 / 语言 / 退出”，只移除系统设置快捷入口。**
   - Why: 这些项分别属于通用账户操作和会话操作；系统设置已有稳定侧边栏入口，继续留在头像下拉中会形成重复入口。
   - Alternative: 进一步把修改密码也迁出用户菜单；被拒绝，因为这会改变现有用户自服务路径，超出本次 IA 调整范围。

6. **前端只增加对 event 型子菜单点击的稳定处理，不为本 change 引入新的菜单类型。**
   - Why: 现有导出中心已经通过 `data-export-center` 事件工作，本次只需要保证当它从 MoreMenu 迁移到侧边栏二级菜单后仍能触发同一事件即可。
   - Alternative: 把导出中心改造成独立路由页；被拒绝，因为这会改变 `export-center-management` 的现有交互语义，并扩大测试范围。

7. **不新增后端 API，只通过菜单数据迁移和现有授权查询结果完成切换。**
   - Why: 菜单重组属于数据和壳层渲染问题，现有 `/menu/query`、授权菜单树和角色菜单关系已足够支撑，不需要引入额外接口。
   - Alternative: 为“组织权限 / 系统设置 / 工具箱”专门增加新的导航聚合接口；被拒绝，因为没有必要，会增加双份来源风险。

## Risks / Trade-offs

- [迁移后的 `core_menu` 层级或排序配置错误，导致管理员导航缺项或重复] → 使用增量 SQL 明确 `pid`、`menu_sort`、`hidden` 调整，并把关键一级/二级路径纳入回归验证。
- [工具箱二级“数据导出中心”在侧边栏点击后被当作路由处理] → 在前端菜单点击工具函数中显式保留 `menu_type='event'` 分支，并增加对应 UI/E2E 覆盖。
- [删除 MoreMenu 后头部布局或交互出现残留样式/空占位] → 同步删除 `Header.vue` 中的组件引用和相关样式入口，避免仅隐藏不删除。
- [帮助链接删除后数据库残留菜单继续进入授权结果] → 迁移中直接删除或彻底隐藏对应 `core_menu` 记录，并校验授权菜单树不再返回这些节点。
- [头像菜单去掉系统设置快捷入口后，管理员短期内找不到原有系统配置入口] → 将系统设置提升为稳定一级导航，并在 proposal/specs 中把这一路径定义为新的唯一治理入口。

## Migration Plan

1. 编写新的 MySQL 迁移，新增「组织权限」一级 group，调整用户/组织/角色/权限/菜单及当前数据库基线中的系统设置/工具箱相关菜单的 `pid`、`menu_sort`、`hidden` 与授权关系。
2. 删除帮助链接相关菜单记录，并保持工具箱下的数据导出中心为二级子菜单，不改动其事件语义。
3. 更新前端 shell：移除 `MoreMenu.vue` 与头部引用，移除用户菜单系统设置快捷入口，并让侧边栏 event 型子菜单继续触发 `data-export-center`。
4. 更新国际化与 E2E 断言，使新的一二级菜单结构和移除后的头部入口都可验证。
5. 上线前执行管理员与普通用户两类菜单回归，确认一级排序、授权可见性、工具箱展开、导出中心触发和用户菜单精简结果都符合预期。
6. 如需回滚，执行反向菜单迁移，恢复原 `core_menu` 层级和帮助/用户快捷入口，并恢复头部 `MoreMenu` 组件引用。

## Open Questions

- 帮助链接相关 `core_menu` 记录在迁移中应采用物理删除还是统一 `hidden=1`；如果历史环境可能依赖这些 ID，需在实施前确认。
- 工具箱一级菜单的 icon 与 locale key 是否沿用现有配置；如果当前数据不完整，需要在实现阶段补齐展示元数据。
- 是否需要在菜单管理页中显式展示“工具箱 > 数据导出中心”为 event 菜单样例，帮助管理员理解该二级项不是普通路由。
