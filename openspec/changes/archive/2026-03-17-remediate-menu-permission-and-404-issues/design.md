## Context

系统当前菜单访问链路可以抽象为：

菜单配置 / 授权数据
-> 前端菜单渲染
-> 路由守卫
-> 页面组件加载
-> 页面初始化 API 请求
-> 后端路由匹配
-> 后端权限校验
-> 最终页面可用性

当前暴露出的主要现象有两类：

1. 用户可以看到菜单，但点击后提示无权限
2. 用户点击菜单或页面初始化时触发 `404`

这说明“菜单是否展示”“页面是否可访问”“接口是否存在”三个层面没有严格对齐。问题既可能出现在前端导航与路由，也可能出现在后端接口实现与权限判定，还可能是两者的契约偏差。

## Goals / Non-Goals

**Goals:**
- 建立菜单访问链路的统一问题分类
- 全量排查核心菜单的权限与 404 问题
- 修复前后端不一致点
- 形成一套可重复执行的专项回归清单
- 明确无权限与资源不存在的运行时语义边界

**Non-Goals:**
- 不重做整套 RBAC/权限模型
- 不对无关菜单做大规模重构
- 不修改 `legacy/` 只读模块
- 不在本次 change 中引入完整 E2E 平台建设

## Decisions

1. **先分类，再修复**
   - 所有问题先按统一模型归类，再进入修复阶段
   - 分类至少包括：
     - 菜单配置错误
     - 前端路由缺失或错误
     - 页面组件加载路径错误
     - 前端 API 地址错误
     - 后端接口缺失或路径变更
     - 权限映射错误
     - 403/404 语义混淆

2. **以“角色 × 菜单 × 结果”矩阵驱动专项测试**
   - 对关键角色建立菜单访问矩阵，记录：
     - 菜单是否可见
     - 菜单点击是否可达
     - 页面初始化是否报错
     - 接口是否返回 403 / 404 / success
   - 修复与验证都以该矩阵为准，而不是依赖零散人工记忆

3. **优先修复核心主路径**
   - 优先级按以下顺序处理：
     1. 主菜单可见但无法进入
     2. 页面一进入即 404
     3. 页面主体可进入但初始化接口 404
     4. 权限反馈与实际授权不一致
     5. 边缘页面或低频功能异常
   - 这样可以先恢复系统可用性，再收敛细节问题

4. **严格区分“无权限”和“资源不存在”**
   - 未授权资源应走权限拒绝路径
   - 真实不存在的资源才返回 404
   - 前端提示与日志语义需可区分，避免误导排查方向

5. **尽量保持修复最小化**
   - 对菜单权限和 404 问题优先做聚焦修复
   - 不借机进行与问题无关的结构性重构
   - 避免在专项治理阶段扩大变更面，提升验证可控性

## Known Issues, Risks, and Follow-ups

### Known Issues

1. **本地运行环境仍存在与本次变更无关的控制台噪音**
   - `/de2api/xpackComponent/content/*` 在当前 Docker 开发环境中持续返回 `501 Not Implemented`
   - WebSocket 长连接存在重复重连与失败日志
   - 这些问题未阻断 `/system/user`、`/system/menu`、`/system/audit*` 页面访问，但会干扰运行态排查信号

2. **菜单组件路径源数据仍存在混用现象**
   - 当前 `core_menu.component` 同时存在 `system/menu`、`system/menu/index`、`audit/dashboard` 等不同写法
   - 本次前端已兼容 `views/<component>.vue` 与 `views/<component>/index.vue` 两类解析方式
   - 兼容修复解决了运行态访问问题，但未从源数据层统一约定

3. **本地 Docker 运行实例可能滞后于当前工作区代码**
   - `:8080` 上的 compose 应用需要重新构建后，才能完整体现当前会话内已完成的前后端修复
   - 因此回归结论以当前代码的静态检查、自动化测试和本地独立运行实例验证为准

### Risks

1. **后端接口映射与权限语义尚未完成全量校验**
   - 本次 change 已完成核心系统菜单相关的接口映射、路由守卫、按钮权限点与授权一致性修复
   - 但更大范围的全站页面、低频模块与历史遗留接口，仍可能存在仓库外运行环境差异或未覆盖场景

2. **后端自动化验证尚未执行**
   - 本次 change 已执行 `apps/backend-go` 下 `make test`
   - 但当前 `:8080` Docker 运行实例可能落后于工作区代码，运行态验证仍应结合重新构建后的环境继续观察

3. **本次回归覆盖范围集中在核心系统菜单**
   - 已完成 `admin` 账号下 `/system/user`、`/system/menu`、`/system/audit`、`/system/audit-dashboard`、`/system/audit-settings` 的真实点击冒烟
   - 其他核心角色、边缘菜单以及授权变更后的回归仍需继续补齐

4. **页面内按钮/API 权限点一致性仍未完成**
   - `4.3` 已完成本次发现的核心错配修复：`interactiveTree` 不再返回占位空对象，页内按钮显隐已重新对齐运行时菜单授权链
   - 但当前仍保留路径别名一致性风险，例如前端 `pathValid` 对 `/dataset-form` 有额外归一规则，而后端业务域授权推导仍主要依赖 `/data/dataset` 等前缀
   - 如后续运行时菜单继续引入新的别名路径，仍需补充针对别名归一的一致性验证

5. **仍存在休眠遗留 API wrapper，但当前主流程不受阻**
   - `apps/frontend/src/api/auth.ts` 中 `resourceTargetPerApi`、`menuTargetPerApi`、`busiTargetPerSaveApi`、`menuTargetPerSaveApi` 目前没有活跃调用点
   - 当前角色管理主流程已切换到 `resourceTreeApi`、`menuTreeApi`、`resourcePerSaveApi`、`roleMenuAuthApi`、`roleMenuAuthSaveApi`
   - 后端对应的 target-permission 兼容接口仍为占位实现；它们不构成当前 `3.2/3.3` 的活跃错配，但若未来重新接入，需要单独补真实语义

### Follow-ups

1. **继续完成 API Mapping and Backend Resource Repair（3.x）**
   - 对非核心页面和低频模块继续做前后端路由一致性核对
   - 清理当前未活跃但仍保留的历史兼容 wrapper，避免未来重新接入时再引入错配

2. **继续完成 Permission Consistency Repair（4.x）**
   - 扩展到更多业务域，继续校验菜单展示、路由守卫、页面内按钮/API 权限点与角色授权结果一致
   - 重点覆盖路径别名归一、低频页面与后续新增权限配置入口

3. **补齐后端验证与更多角色回归**
   - 在重新构建后的 Docker 运行环境中复核当前修复结果
   - 在浏览器中增加非管理员角色与更多菜单域回归，形成更完整的“角色 × 菜单 × 结果”验证矩阵

4. **在后续治理中统一菜单组件路径约定**
   - 建议逐步将 `core_menu.component` 收敛为单一约定，避免长期依赖前端兼容分支
   - 优先统一系统管理域与审计域菜单配置，降低后续新增菜单再次引入路径混用的概率
